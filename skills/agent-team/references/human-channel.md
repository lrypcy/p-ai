# 人机通道：Team Leader ↔ 用户

## 为什么需要这条通道

agent 团队里**最危险的不是 agent 干得慢，而是 agent 自己拍板**。上一版设计里 lead 有 Stop Conditions 挡着「撞契约冲突就停」，但缺一个出口：**停下之后找谁、问什么、问到什么程度、用户不在线怎么办**。

这条通道的价值不是「通知进度」，而是**把决策权在关键节点交回给人**。

## 能力分级：先说清IM 能做什么、不能做什么

多数人以为「配了飞书就能双向对话」，但实际有硬边界。设计前必须认清：

| 层级 | 能力 | 依赖 | 适用范围 |
| --- | --- | --- | --- |
| **L0 出向通知** | lead → 用户：发消息（进度、提问、结论） | 群机器人 webhook URL（飞书/企微/钉钉均有） | 提问、汇报、告警。**最常用，绝大多数场景够用** |
| **L1 出向 + tmux 入向** | 用户回复不用离开终端：`tmux attach` 到 lead 窗口直接回答 | L0 + tmux | **推荐默认档**。零额外依赖，响应最快，且天然带完整上下文 |
| **L2 全双向 IM** | 用户在飞书里回复，lead 自动收到 | **飞书应用**（非群机器人）+ 事件订阅 + 消息 API | 需要用户离开终端时。配置成本最高，多数场景不值得 |

**必须诚实说明的限制**：

- **webhook 只能发不能收**。飞书/企微的「群机器人」是单向通道——lead 能发消息给你，但你在群里回一句 lead 收不到。这是 L0 的根本限制。
- **微信个人号没有官方 webhook**。企业微信有（群机器人 webhook），个人微信没有合规方案——不要用非官方 hook 库，涉及账号风险。
- 推荐的组合是 **L1**：飞书 webhook 负责「重要的事主动推给你」，tmux attach 负责「你有问题时随时进来答」。既不重复配置也不需要 IM 应用的繁琐配置。

## L2 全双向：飞书应用路径（当前仅确认与预留，尚未实现）

**当前状态：初始化时会向你确认是否有可用的飞书应用，但 `teamctl.py` 尚未实现消息接收。** 在实现落地前，L2 配置会被记录但**入向仍走 tmux attach**——不要误以为配了 L2 就能在飞书里回复。

### 为什么是飞书应用而不是群机器人

群机器人只有 webhook 出向能力。要双向，必须用**飞书自建应用**，它多了一样东西：**事件订阅（Event Subscription）** —— 应用可以向飞书注册回调地址，用户发给应用的消息会以事件推给你。

| |群机器人（webhook） | 飞书自建应用 |
| --- | --- | --- |
| 出向发消息 | ✅ webhook URL | ✅ API（更规范，支持富文本/卡片） |
| 入向收消息 | ❌ | ✅ 事件订阅 |
| 需要公网回调地址 | ❌ | **✅ 需要**（飞书要能POST 到你） |
| 凭证 | URL 本身即凭证 | `app_id` + `app_secret`（**敏感**） |
| 配置成本 | 1 分钟 | 30~60 分钟（建应用、申请权限、设回调、做公网穿透） |

**公网回调地址是关键门槛**：本地机器拿不到公网入口，需要内网穿透（ngrok / cloudflared / 自建 frp）。这不只是配置麻烦，还意味着要长期保持一个穿透隧道在线。所以**除非你确实经常需要离开终端，否则 L1 够用**。

### 如果你有可用的飞书应用，初始化时要确认这几件事

在确认档位时若用户选 L2，逐项确认（**不要跳过，也不要凭空假设**）：

| # | 确认项 | 说明 |
| --- | --- | --- |
| 1 | 是否已有飞书自建应用 | 有则复用；没有则先在飞书开放平台建，**本skill 不代建** |
| 2 | `app_id` / `app_secret` | **绝不写进配置文件或提交进 git**。只记环境变量名（`--app-id-env` / `--app-secret-env`） |
| 3 | 应用已申请的消息权限 | 至少需要「接收用户单聊消息」的权限；权限不足会静默收不到消息 |
| 4 | 事件订阅的接收方式 | 飞书提供长连接（websocket，无需公网）与「将事件发送至开发者服务器」（需公网回调）两种。**推荐长连接**——它绕开了公网穿透这个最大障碍 |
| 5 | 回调/长连接是否已验证可用 | 未验证的 L2 不能算配置成功 |

**推荐用飞书的长连接模式**：飞书 SDK 支持客户端主动建立 websocket 长连接，不需要任何公网地址，能绕过「本地机器无法接回调」这个最大障碍。这也是 L2 唯一能低成本落地的路径。

### 当前阶段的处理方式

`teamctl.py` 现在的行为：

- `im init --tier L2` 会把L2 配置**记录下来**（含应用凭证的环境变量名与接入方式），但打印明确警告：**入向尚未实现，请用 tmux attach 回答**
- `im check` / `im status` 显示 L2 状态为「已登记，入向未实现」
- `im ask` 在 L2 档位下**仍通过 webhook 或 tmux 出向**，并提示用户用 `tmux attach` 回答
- L2 的入向接收将在后续版本实现，实现后本节会移除

这样处理的好处是：**先把配置和意图记下来**，等你确实需要时不用重新调研；但不会造成「配了却以为能用」的误解。

## 初始化时的确认流程

在 Step 2~4 之间执行（agent-team 与 init-exp 都要做）：

### 1. 先检查是否已配置（幂等）

**这一步不能跳过。** 重复配置会造成两个IM 机器人对同一件事说两遍，或让用户被重复骚扰。

```bash
scripts/teamctl.py im check
```

判定逻辑：

| 检查结果 | 动作 |
| --- | --- |
| 已配置且`verified_at` 存在，且项目级无覆盖 | **直接复用，不要问用户**，打印通道信息后继续 |
| 存在全局配置（`~/.workbuddy/agent-team/im.json`）但本项目未声明 | **询问用户是否复用全局通道**，不要重新问一遍 webhook |
| 存在但`verified_at` 为空（配了没验证过） | 执行一次发送验证；失败则询问是否重配 |
| 不存在 | 走下面的新配置流程 |

**全局 vs 项目级**：

- **全局**（`~/.workbuddy/agent-team/im.json`）：一台机器一个飞书机器人，所有团队复用。**强烈建议默认走全局**——同一个飞书机器人跟各个团队的 lead 对话，按项目群或前缀区分即可。
- **项目级**（`<team>/logs/im-channel.json`）：只有该项目要特殊通道（如发到特定群）时才建，且**优先从全局继承后覆盖单字段**，而不是整份重填。

### 2. 新配置流程（仅当确实没有）

依次确认五件事，**每件都给出默认建议，不要逐条追问**：

| # | 确认项 | 选项 | 默认 |
| --- | --- | --- | --- |
| 1 | 是否配置 IM 通道 | 是 / 否 | **是**（有通道的团队明显更安全） |
| 2 | 通道类型 | 飞书 / 企业微信 / 钉钉 / 其他 / 暂不配置 | 问用户实际用哪个，**不要猜** |
| 3 | 能力档位 | L0 只发 / **L1 加 tmux 入向** / L2 飞书应用全双向 | **L1** |
| 4 | **是否有可用的飞书自建应用**（仅当考虑 L2 时问） | 有 / 没有 / 不确定 | 无则回落到 L1 |
| 5 | webhook URL | 由用户提供 | 无。**绝不能凭空编造或复用别人的 URL** |

**第 4 项怎么问**：直接问"**你有没有已经建好的飞书自建应用？**"，不要问"要不要我帮你建"——建应用要在飞书开放平台手工操作，本 skill 做不了。

```
有 → 确认 app_id/app_secret 放在哪（只记环境变量名）+ 消息权限是否已申请
     + 用长连接还是回调（推荐长连接，见上文 L2 章节）
没有 / 不确定 → 建议留在 L1，如实说明 L2 的门槛（建应用 + 申请权限 + 处理公网回调）
明确要 L2 但还没建 → 可以先登记意图，但必须明确告知「入向暂不可用，回复请走 tmux」
```

用户选「暂不配置」→ 在 TEAM.md 记 `im_channel: none`，lead 遇到需要确认的事**停下并在对话里直接问用户**，不自行发挥。

### 3. 写入配置

```bash
# 默认推荐 L1
scripts/teamctl.py im init --channel feishu --tier L1 \
  --notify-cmd 'curl -s -X POST -H "Content-Type: application/json" -d @- "$FEISHU_WEBHOOK"' \
  --webhook-env FEISHU_WEBHOOK

# 有飞书应用、想登记 L2 意图（入向尚未实现，命令会提示）
scripts/teamctl.py im init --channel feishu --tier L2 \
  --notify-cmd 'curl -s -X POST -H "Content-Type: application/json" -d @- "$FEISHU_WEBHOOK"' \
  --webhook-env FEISHU_WEBHOOK \
  --app-id-env FEISHU_APP_ID --app-secret-env FEISHU_APP_SECRET \
  --app-verify-mode longconn
```

**URL 存法有讲究**：只存**环境变量名**（`--webhook-env`），不把 URL 明文写进配置文件。配置文件通常会进 git，明文 webhook 等于把机器人权限公开。

写入后立刻发一条验证消息：

```bash
scripts/teamctl.py im test
```

验证成功才写`verified_at`。**验证失败不算配置成功**——不允许「配了但没验过」的状态存在。

## lead 什么时候该问、什么时候该自己干

这是这条通道最核心的部分。**约束不是「少问」，而是「问对」**——无约束地发消息会训练用户忽略通知，比不通知更糟。

### 必须问（ask-required）

| 情形 | 为什么 |
| --- | --- |
| 契约未定义的语义 |猜错会静默污染下游 |
| 需要超出契约授权的决策 | 契约的 Do-Not-Touch 就是边界，越界必须问 |
| 不可逆操作 |删数据、改配置、对外发布、force push |
| 会显著影响范围或成本的决定 | 加角色、改预算、砍目标 |
| 多次重试仍失败（≥7次） | 此时该问的是「这任务还该不该做」，agent 无权决定 |
| 目标本身看起来不合理 | 例：验收标准与用户真实意图明显不符 |
| 需要用户提供上下文才能继续 | 契约 Inputs 指向的信息不存在 |

### 可以自己定（ask-omitted）

| 情形 | 为什么不算越界 |
| --- | --- |
| 契约 Task 段已明确覆盖的实现细节 | 已经在授权范围内 |
| Do-Not-Touch 与 Done Criteria 已界定的范围内的技术选型 | 属于实现层决策 |
| 可逆的局部调整 | 错了能改回来，且不影响下游 |
| 已记录的决策的常规应用 | decisions.md 已裁定，不重复问 |
| 格式/命名/排序等纯形式问题 | 无实质影响 |

### 禁止（ask-forbidden）

| 情形 |
| --- |
| 绕过 Stop Conditions 直接动手 |
| 用户已明确回答过的同一问题（记进 decisions.md，避免重复骚扰） |
| 为省事跳过验证步骤 |
| 用「我以为」代替确认 |

### 提问的纪律

**一次问一件事。** 把三个问题打包发过去，用户会只回答最显眼的那个。

**必须给选项，不要开放式提问**。开放式提问（「你怎么看？」）把思考成本推回给用户；选项式提问让用户只需判断。

```
❌ 收录计划需要调整，是重构还是硬加？
   ↑ 开放式，用户得自己想方案

✅ T2 收计划有三个方案，选哪个？
   A. 重构到插件层（改动大，但加新计划只改一处）
   B. 硬加到主文件（今天能完，但每次加都要动两处）
   C. 先硬加上，下个迭代再重构（今天能完 + 留了重构路径）
   背景：三处 业务逻辑重复，A 是根治，B/C 是妥协
   → 回复 A / B / C，或说其他
```

**带上背景与代价**。用户不在你的上下文里，无法凭空判断。要给：当前卡在哪、已试过什么、每个选项的代价。

## 用户不在线时怎么办

IM 通道**天然是异步的**——发完消息用户可能几小时后才看到。默认「发出去就停着等」会让团队卡死。

`auto_default` 机制：lead 在提问时给出**默认动作**和**等待时长**。

| 提问类型 | 默认动作 | 说明 |
| --- | --- | --- |
| 阻塞其他所有任务 | **停** | 等用户。宁可停也不要猜 |
| 只阻塞自己、且可并行 | **继续做不依赖的部分**，把挂起任务标 `awaiting_user` | 不浪费 |
| 超软超时仍未答复 | **按契约最保守的解释推进**，并登事件标注`auto_resolved` | 明确记下来，不当作用户确认过 |

**绝对不允许**：超时时「按我自己的理解优化一下」且不记录。这正是要防止的自行发挥。

```bash
# lead 提问时同时设置默认动作
scripts/teamctl.py im ask --task T3 --severity blocker \
  --question "..." --options "A. ...|B. ...|C. ..." \
  --default "B" --auto-after-min 120
```

答复后：
```bash
scripts/teamctl.py im answer --id M<ts> --reply "B，就这个" --by user
```

**答复必须落盘**：写进 `decisions.md`（为什么这么选）+ 事件流。lead 冷重启后必须知道「这个决定是用户拍的」，否则会重新讨论。

## 与黑板、上报通道的关系

三条通道职责不重叠：

| 通道 | 方向 | 传什么 | 持久性 |
| --- | --- | --- | --- |
| **IM 通道** | lead ↔ 用户 | 决策请求、授权、进度汇报 | 事件留档，答复必须写进 decisions.md |
| **上报通道**（governance.md） | worker → lead | 过程中的疑问与阻塞 | `inbox.jsonl` + 事件 |
| **黑板** | worker 全体 | 任务、产出、决策记录 | 落盘文件 |

**决策权是分层的**：worker 不直接问用户（必须经lead），只有 lead 能发起 IM 提问。这保持了「用户只需面对一个对话方」，否则用户会被 N 个 agent 同时问住。

## 团队纪律

- **一个人类对话方**：所有 IM 消息都由 lead 发/收，其他角色不上报用户。
- **不刷屏**：同一个议题的追问合并为一条；`info` 级别的进度只在里程碑和收摊时发。
- **可离线**：用户不在线时，按 auto_default 走并标注，不静默等待也不静默发挥。
- **保密**：IM 消息里不放完整契约与产出全文，只给路径与摘要（产出让用户自己打开看）。
- **可回溯**：所有 IM 提问/答复都进事件流，收摊时能在归档里看到「哪些决定是用户拍的」。
