# 上下文协议：刚好够用

## 问题定义

多 agent 团队的上下文失败有两种形态：

- **饥饿（under-fed）**：agent 不知道边界在哪、不知道产出放哪，瞎猜、重复劳动、改错文件
- **过载（over-fed）**：把所有背景、所有历史、所有别人的进度都塞给它，上下文被无关信息稀释，注意力被稀释、成本上升，且信息容易过期

目标不是"给最少"，而是**最小充分上下文**：完成本任务所需的全部信息，不多不少。

## 三层披露模型

借鉴 Skills 的渐进式披露，agent 上下文也分三层。

| 层 | 内容 | 加载时机 | 体量约束 |
| --- | --- | --- | --- |
| **L1 常驻** | `TEAM.md` 的团队目标 + 自己的那一行 + 自己的契约 | agent 启动时一次性读入 | **≤ 200 行**，超了就压缩 TEAM.md 里的团队目标段 |
| **L2 按需** | 契约里 Inputs 段列出的文件（给路径，agent 自己读） | 执行任务过程中自行读取 | 按需读，不预先全量粘贴 |
| **L3 引用** | 大文件、原始数据、历史会话、参考实现 | 只在契约明确指向时打开 | **永不预先注入**；只给路径 + 为什么需要它 |

### L1 该放什么

- 团队最终目标（一段话）
- 自己的角色、职责边界
- 自己的 Done Criteria
- 团队协作规则（黑板在哪、产出放哪、怎么汇报）
- 自己当前的会话/ checkpoint 指针

### L1 绝不该放什么

- 整个仓库的目录树
- 别的 agent 的完整对话历史
- 全部决策记录（只给与本任务相关的条目 + 指针）
- 通用编程常识

## 上下文契约八段详解

契约是**lead 与 agent 之间的接口定义**，落盘在 `contracts/<role>.md`。

### 1. Identity

一句话说清"你是谁"。示例：

> 你是本团队的 **builder-a**，负责 `src/api/` 下的实现工作。

不要写性格描述，agent 不需要"你是一个严谨的工程师"这种人格设定，只需要职责。

### 2. Objective

本轮要达成的目标，引用 `tasks.md` 的任务号，让契约与看板双向可追溯：

> 目标：完成 T3 —— 为 `/api/search` 增加分页参数。目标是 G2 的必要子步骤。

### 3. Task

具体做什么，边界在哪。写清范围与顺序，避免 agent 自行扩大范围：

> 按 `docs/api-design.md` 的约定，为 `src/api/search.py` 增加 `page`/`page_size` 两个可选查询参数，
> 默认 `page=1`、`page_size=20`，上限 100。需要同时更新 `tests/test_search.py`。

### 4. Do-Not-Touch（最容易被忽略、最该写）

禁止修改的文件/目录，以及禁止决策的领域：

> 禁止修改：
> - `src/api/__init__.py`（由 builder-b 负责）
> - `tests/` 下的其他文件
> - 任何依赖文件（`pyproject.toml`）—— 需要新依赖时先上报 lead
>
> 禁止决策：
> - 分页参数命名（已由 G2 决策固定，见 decisions.md D3）
> - 错误码语义

### 5. Deliverables

产出落到哪、什么格式、怎么命名。**路径要精确到文件名**：

> 产出：
> - `src/api/search.py`（实现）
> - `tests/test_search.py`（新增3 个用例：默认分页、显式页码、超上限截断）
> - `results/T3-report.md`（一段不超过 10 行的说明：改了什么、怎么验证过）

### 6. Inputs（给路径，不给全文）

上游产出在哪、该读哪些文件、按什么顺序：

> 阅读顺序：
> 1. `TEAM.md`（团队目标与协作规则）
> 2. `tasks.md`（找 T3 行）
> 3. `decisions.md` 的 D1、D3 条目（分页参数已定的决策）
> 4. `docs/api-design.md`（接口约定）
> 5. `src/api/search.py`（现状）
>
> 不需要读：其他 builder 的工作目录、tests/ 下的其他文件。

**关键**：写路径 + 理由，让 agent 自己读。粘贴全文会导致上下文膨胀 + 内容过期后仍被当成事实。

### 7. Done Criteria（必须可核验）

lead 会据此核验，所以每条都要能用**命令**或**文件事实**验证：

好的写法：
- `pytest -q tests/test_search.py` 全绿且输出含 `3 passed`
- `results/T3-report.md` 存在且包含"验证方式"段
- `src/api/search.py` 中 `page_size` 上限为 100（grep 可确认）

坏的写法：
- 代码质量良好
- 功能可用
- 完成了需求

### 8. Stop Conditions

什么情况必须停下上报，而不是硬猜。这是**防跑偏的最后一道闸**：

> 遇到以下情况立即停止并在 `notes.md` 记录后上报 lead，不要自行决定：
> - 契约与 `docs/api-design.md` 冲突（以哪个为准由 lead 判断）
> - 发现 `tests/test_search.py` 里已有他人未提交的改动
> - `page_size > 100` 的截断语义不确定
> - 需要改契约里列为禁止的文件

## 黑板模式：团队如何交换信息

**不通过 agent 互相对话**，全部通过共享文件。理由：agent 之间没有共同记忆，对话是唯一信息会被漏读/截断的通道。

### 单写者原则

每个文件有且只有一个写入者，读取者可以多个：

| 文件 | 唯一写入者 | 读取者 |
| --- | --- | --- |
| `tasks.md` | lead | 全员 |
| `decisions.md` | lead | 全员 |
| `contracts/<role>.md` | lead | 对应 agent |
| `results/<own-task>.md` | 对应 agent | lead、reviewer、相关下游 |
| `notes.md` | 全员追加（只追加，不改他人行） | 全员 |

这直接消灭了"两个 agent 同时改一个文件"的冲突源。

### 传递单位是"产出 + 指针"，不是"对话历史"

下游 agent 需要上游信息时，读的是上游写在文件里的**结论**，而不是上游的思考过程。这样：

- 上下文小（只读结论）
- 结论过期可被发现（文件有更新时间戳）
- 上游可以放心退休（信息已落盘）

### 上游没写产出 = 任务未完成

这是团队的硬规则。**下游 agent 发现上游产出缺失时，不得自己动手补做上游任务**，应停下上报 lead。否则任务链条会出现"幽灵完成"：没人知道哪步是谁做的。

### 过程中的疑问：走上报通道，不走横向 peer

黑板传的是**结论**（异步持久、跨任务有效）。但 agent 执行途中会撞到**当下就需要答案**的问题——契约没定义的语义、上游还没产出的东西、两个方案不知选哪个。这类问题的传递方式是**向上 escalate**（详见 `governance.md`）。

三条硬约束：

1. **只能向上找 lead，不能横向找 peer**。横向通信会制造多源真相与互相覆盖。
2. `blocker` 级必须停下等答复，不自行拍板。
3. **答复结论要落盘**进契约补充或 `decisions.md`——否则只存在于 lead 会话里，冷重建的 agent 拿不到。

在契约的 Stop Conditions 段之后追加一条执行指令：

> 遇到契约未覆盖的不确定点时，用 `escalate --severity blocker` 上报 lead，
> 不要自行决定，也不要横向询问其他 agent（横向通道不支持）。

**若该角色以 goal 模式启动**（主 agent 默认，opencode 下为 `ulw`），上面这段与 Stop Conditions
第 8 段、第 9 段都是**强制项，不能省**。goal 模式的默认行为是「目标不清就自行假设并推进」，
与本skill「不得自行发挥」直接冲突；契约必须显式压制这个默认：

```markdown
> 本任务以 goal 模式执行。你只拿到目标，不会有步骤清单——**但凡契约未覆盖的情况，
> 一律不要自行假设**：用 `escalate --severity blocker` 上报 main；
> 若你是 main，用 `im ask` 向用户确认。预算软超时即checkpoint 收摊，不要硬撑到目标完成。
```

在契约的 Stop Conditions 段之后追加一条执行指令：

> 遇到契约未覆盖的不确定点时，用 `teamctl.py escalate --severity blocker` 上报 lead，
> 不要自行决定，也不要横向询问其他 agent（横向通道不支持）。

**lead 的契约额外追加「向用户确认」段**（非 lead 角色不需要）：

```markdown
## 9. 向用户确认（仅 lead）

需要用户拍板的情形：
- 契约未定义的语义
- 超出本契约授权的决策（见 Do-Not-Touch）
- 不可逆操作（删数据 / 改配置 / 对外发布 / force push）
- 显著影响范围或成本的决定
- 同一任务退回 >=7 次
- 目标本身看起来不合理

提问方式（必须遵守）：
- 一次问一件事，给 2-3 个选项，不要开放式提问
- 附背景：当前卡在哪、已试过什么、每个选项的代价
- blocker 级停下等答复，不得自行决定
- 用户答复后写进 decisions.md，并更新本契约相关段落
```

## 上下文裁剪清单

投放契约前，lead 自查：

- [ ] 契约里没有任何大段代码/日志粘贴（只给路径）
- [ ] Inputs 段没有指向 agent 根本不用的文件
- [ ] `TEAM.md` 团队目标段不超过 50 行
- [ ] Done Criteria 每条都能用命令或文件事实验证
- [ ] Do-Not-Touch 不为空（哪怕只禁一个文件）
- [ ] Stop Conditions 至少覆盖一类不确定性
- [ ] 契约总长< 100 行
- [ ] 已声明上报通道（escalate 到 lead），并写明不横向问 peer

## 上下文恢复时的重建顺序

agent 会话丢失需要冷重建时，按此顺序重建（不可跳步）：

1. `TEAM.md` 团队目标段 → 知道为什么做
2. `decisions.md` 相关条目 → 知道已定什么
3. `logs/checkpoints/<role>-<task>.md` → 知道做到哪一步
4. `contracts/<role>.md` → 知道边界与完成标准
5. `results/` 已有产出 → 知道不用重做什么
6. `tasks.md` 自己那一行 → 知道当前状态

顺序颠倒会导致 agent 重复劳动或推翻已有决策。
