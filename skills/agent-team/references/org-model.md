# Agent Team 组织模型

## 设计依据：把人类团队的协作方式映射到 agent

真实团队的运转依赖三件事，agent 团队同样需要：

| 人类团队 | Agent 团队 | 实现载体 |
| --- | --- | --- |
| 每个岗位有清晰的职责边界与汇报线 | 角色 + 契约 + 单一负责人在tasks.md | `contracts/<role>.md` + `tasks.md` |
| 交办任务时讲清"要什么、别碰什么、怎么算完" | 上下文契约八段 | `contracts/` |
| 会议结论、当天进度要落到白板 | 共享黑板文件 | `notes.md` / `decisions.md` / `tasks.md` |
| 下属干完活，上级要看实物再验收 | lead 打开 `results/` 产物核验 | 完成判定环节 |
| 跑完一个项目就散场，需要时再重组 | retire / resume 生命周期 | `teamctl.py` |
| 值班交接要留记录 | checkpoint + 事件流 | `logs/` |

## 角色库

按需设置，**不要为了凑齐角色表而设岗**。下表是常用角色及其最小职责。

### lead（主导者）

团队唯一对用户负责的角色。

- **职责**：制定目标、拆分任务、分配、裁决冲突、核验产出、对外汇报
- **必为 resident**：需要持续掌握全局状态、随时被打断追问
- **不要做**：亲自写所有代码。lead 一旦陷进实现，就失去全局视角
- **权威文件**：`tasks.md`、`decisions.md`

### researcher（调研员）

只做信息收集与验证，不改代码。

- **职责**：查文档、读源码、找数据、做对比、给出带链接/行号的结论
- **默认 ephemeral**：任务天然边界清晰（"查清X API怎么用"）
- **产出**：`results/<topic>.md`，必须有出处
- **不要做**：顺手改代码；发现 bug 记录并交 lead 派给 builder

### builder（执行工程师）

把任务变成实际产物。

- **职责**：写代码/跑实验/写文档，产出落在 `results/` 或指定源码路径
- **模式判定**：连续多任务共享大上下文（如同一模块重构）→ resident；否则 ephemeral
- **不要做**：改契约划定范围外的文件；自行扩大技术栈/引入新依赖而不报备

### reviewer（评审）

独立于执行者的质量关卡。

- **职责**：按Done Criteria 核验产出、找缺陷、指出具体行号/文件
- **默认 ephemeral**：评审是一次性动作，评完即退
- **关键约束**：**不要让 builder 自评**。自己写自己验会系统性放过问题
- **产出**：`results/review-<task>.md`，结论写 pass / needs-revision + 理由

#### 独立性分级（软约束，按重要性递增）

reviewer 的独立性不是全有全无，**按验收的重要程度分档**：

| 档位 | 做法 | 适用 |
| --- | --- | --- |
| **最低要求** | reviewer ≠ builder（不同角色，不自己验自己） | 所有情况，无例外 |
| **推荐** | reviewer 与 builder 用**不同 agent CLI 或不同模型** | 重要验收：安全相关、数据正确性、对外交付 |
| **理想** | reviewer 用不同 CLI + 不同上下文管理实现 | 架构级评审、争议性判定的终裁 |

**为什么推荐换CLI/模型**：同模型倾向于用自己的推理路径去"确认"自己的结论——它会认为 builder 的实现是合理的，因为如果不合理，它自己也会那么写。换一个 CLI/模型相当于换一副脑子，能发现同盲区看不见的问题。

**不要强求**：如果只有一个 CLI 可用，同模型 reviewer 仍远好于没有 reviewer。独立性是加分项，"不自己验自己"才是底线。

**记录独立性**：在 `TEAM.md` 的 roster 里记下每个角色实际用的 CLI，方便验收时判断该用哪档。`status` 会显示各角色的 CLI 归属。

### recorder（记录员）

可选，用于长周期或审计要求高的场景。

- **职责**：把过程中的口头结论转成 `decisions.md` 条目、汇总 `notes.md`
- **何时需要**：任务跨越多天、参与 agent 多、结论会被后续引用
- **通常不做**：短任务里由 lead 顺手记即可

## 职责边界矩阵

填这张表进 `TEAM.md`，防止越界。

| 角色 | 可改文件 | 可做决策 | 禁止 | 报告给 |
| --- | --- | --- | --- | --- |
| lead | 全部 | 任务分配、验收、方案终裁 | 直接大规模改实现代码 | 用户 |
| researcher | `results/*` | 调研方法 | 改源码 | lead |
| builder | 契约指定的源码路径 | 实现层技术选型 | 改契约外文件、扩依赖不报 | lead |
| reviewer | `results/review-*` | 验收结论 | 直接修 bug、评审自己的产出 | lead |

再加一列实际使用的 CLI，用于判断 reviewer 独立性档位：

| 角色 | 实际 CLI | 说明 |
| --- | --- | --- |
| lead | <cli> | |
| reviewer | <cli，理想情况与 builder 不同> | 不同 CLI/模型能发现同盲区看不见的问题 |

**冲突时的通用规则**：两个 agent 想改同一个文件 → 立即停下上报 lead，由 lead 决定合并顺序或拆分文件。这是多agent 并发最高频的失败模式。

**验收时的独立性检查**：lead 在判定 pass 前确认 reviewer ≠ builder。需要更高独立性档位时（见上节），在派 reviewer 任务时就指定不同 CLI，而不是事后要求。

## 规模梯度

从最小梯度开始，**不够再往上加**。每加一个角色就多一份契约维护成本和多一份上下文开销。

### `solo`（1 agent）

lead 兼任所有工作。适用于：任务单一、上下文自洽、不需要并行。

省掉所有协作开销，但**必须留 `results/` 与 `notes.md`**，否则事后无法复盘。

### `duo`（lead + 1 执行）

lead 负责目标与验收，执行者负责产出。适用于：需要有人核验，但不需要分工调研。

最常见的最小可用团队。reviewer 职责由 lead 兼任（lead 不写实现代码，因此自评偏差较小）。

### `squad`（lead + 2~4 执行/调研/评审）

大多数真实任务。适用于：任务可并行拆成 2 条以上独立线。

### `council`（N 平级专家 + 1 裁决者）

用于方案取舍、技术选型争论、评审争议。裁决者可以是 lead，也可以是用户。

**不要在任务交付物清晰时用 council**——纯讨论不产出，等于没开工。

## 角色规模速查

| 任务类型 | 建议梯度 | 典型角色组合 |
| --- | --- | --- |
| 写一个函数/修一个 bug | `solo` | lead（= 执行） |
| 一次完整实验并出报告 | `duo` | lead + builder |
| 调研 3 个技术方案并选型 | `council` | lead + 3 researcher |
| 大型重构（多模块并行） | `squad` | lead + 2 builder + 1 reviewer |
| 端到端交付（调研→实现→验证→文档） | `squad` | lead + researcher + builder + reviewer |
| 长期维护型项目 | `squad` + 部分 resident | lead(resident) + builder(resident) + researcher(ephemeral 按需拉起) |
